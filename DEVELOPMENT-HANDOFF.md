# Продолжение разработки маршрутизации

Ветка сохраняет незавершённую работу поверх v2.2.0. В релиз её пока включать рано.

## Требования

- Пользователь выбирает оба адаптера в QuickDNS. Ethernet 2 и Ethernet 6 — имена в исходном тесте.
- Новые соединения выбранного EXE или MSIX идут через второй адаптер. Остальные приложения используют основной, даже если через него доступны только локальные ресурсы.
- При отключении второго адаптера новые соединения выбранного приложения блокируются без перехода на основной.
- Маршрутизация приложений — дополнительная функция. Portable-сборка содержит sing-box и распространяется одним EXE.

## Что есть в коде

- `src/split_routing.cpp` генерирует конфигурацию sing-box 1.14.4 и управляет TUN. `src/dialog_app_routing.cpp` связывает её с UI.
- Для MSIX сопоставляется путь пакета. У Codex учтён отдельный версионный backend из LocalAppData.
- Отключён автоматический DNS-перехват TUN. TCP/UDP 53 к настроенным IPv4-резолверам направляется через адаптер, которому они принадлежат. Общий резолвер использует основной адаптер. Есть отдельное правило DoH для svchost.exe к IPv4-резолверам второго адаптера.
- Windows DNS Client общий для приложений. Правила по адресу резолвера не гарантируют DNS-изоляцию по приложению. Защитные фильтры из `src/app_route_guard.cpp` не подключены к текущему TUN-сеансу. Их нельзя включать без проверки, что соединения клиента через TUN остаются разрешёнными.

## Что установлено

- После перезапуска Codex при активном TUN и отключённом основном адаптере наблюдались TCP-сокеты Codex на TUN и исходящие сокеты sing-box на втором адаптере к тем же адресам.
- При обоих включённых адаптерах пользователь воспроизвёл сбой соединения. В момент сбоя не удалось сопоставить конкретный запрос с процессом, выходом sing-box и резолвером.
- Журнал показывал обращения к DNS второго адаптера через основной выход и недоступность публичного IPv6 через второй. Часть обращений HTTPS к DNS шла через основной выход даже со scoped-правилом DoH. Не установлено, какой процесс инициировал эти обращения.
- 27 локальных тестов прошли. sing-box принял конфигурацию. Это не подтверждает сценарий с двумя адаптерами или блокировку при отключении второго.

## Сборка и диагностика

Windows x64, CMake и MSVC. Из Developer PowerShell:

```powershell
cmake -S . -B build -DQUICKDNS_EMBED_SING_BOX=ON
cmake --build build --config Release
ctest --test-dir build -C Release -LE network --output-on-failure
powershell -NoProfile -File scripts/observe-routing.ps1 -DurationSeconds 300
```

Наблюдатель сохраняет последовательные снимки интерфейсов и сокетов, конфигурацию и журнал активного сеанса в %TEMP%\quickdns-observer-*. Для контрольного приложения задайте `-AdditionalProcessNames`. Снимки UDP не показывают удалённую сторону. Для доказательства маршрута UDP нужен сетевой захват или журнал сервера. Сырые снимки содержат локальные имена, пути и адреса. Храните их локально.

### Автоматическая проверка на Windows

Запустите из PowerShell с правами администратора после сборки со встроенным движком. Подставьте имена из `Get-NetAdapter`. Первый интерфейс должен иметь интернет, второй — только локальную связь.

```powershell
powershell -NoProfile -File scripts/test-routing-live.ps1 -BuildDirectory build -InternetAdapter 'Wi-Fi' -LocalAdapter 'VirtualBox Host-Only'
```

Сценарий запускает sing-box с конфигурацией QuickDNS и меняет роли адаптеров. Два экземпляра curl по разным путям проверяют HTTPS с закреплённым IP и с обычным разрешением имени. `-DisconnectAdapter 'USB Ethernet'` добавляет отдельный прогон с третьим адаптером, у которого есть интернет. Сценарий временно отключает этот адаптер, проверяет блокировку выбранного приложения и доступность контрольного, затем возвращает адаптер и проверяет восстановление. `-CheckCodex` повторяет проверку для HTTP и WebSocket через `codex doctor` из работающей установки Codex MSIX. Подробные результаты и журналы сохраняются в %TEMP%\quickdns-live-*.

На тестовом ПК фиксированное имя Wintun приводило к зависанию повторного старта после принудительной остановки движка. Новый сеанс теперь получает собственное имя TUN. Три последовательных запуска через `SplitRoutingSession` со встроенным движком прошли. Сценарий с Wi‑Fi, VirtualBox Host-Only и USB‑Ethernet прошёл для двух EXE и установленного Codex. Исходный сбой на рабочих Ethernet 2 и Ethernet 6 остаётся без воспроизведения на исходной сети.

## Следующий эксперимент

1. В Windows-ВМ с двумя приватными сетями Hyper-V оставить основной адаптер без интернета, но с локальным HTTP и DNS. На втором дать доступ к HTTPS и DNS. Физический адаптер использовать только при финальной проверке.
2. Запустить наблюдатель до QuickDNS. Сделать свежие запросы из двух тестовых EXE с разными путями. Для целевого процесса сравнить HTTPS с известным IP и обычный запрос по имени. Сверить исходящий адрес на тестовом сервере. Для контрольного процесса подтвердить локальный доступ через основной адаптер.
3. По результату исправить привязку выхода или DNS. Проверить отключение второго виртуального адаптера, отсутствие перехода на основной, восстановление после подключения и остановку движка.
4. После прохождения стенда проверить новый запрос Codex после перезапуска при обоих активных физических адаптерах и блокировку при недоступности второго. Автоматически сохранить данные до возможного обрыва связи.

На исходной машине Hyper-V установлен, но токен процесса не имел прав управления ВМ. Для стенда понадобится доступ к Hyper-V и Windows-гость.
